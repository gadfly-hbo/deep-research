# PRD — 独立深度研究工作台 第一期(v1.0)

> 规格源头:`.flow/proposal.md`(产品方案 v1.0)。本 PRD 只做 elaboration 与缺口填充;与 proposal 的差异全部列在文末"PRD-vs-proposal 差异",须经用户确认。
> 无 issue tracker 配置,PRD 落于 `.flow/prd.md`(to-prd 技能的降级路径)。

## Problem Statement

品牌与行业研究者(咨询、投研、品牌方、战略岗)面对一个两难:通用 AI 深度研究能快速产出长篇报告,但引用不可核、数据口径混用、结论与证据脱节,使用者仍需花数小时人工抽查才能敢用;而纯人工研究质量可控却以周计成本。研究者缺少一个能把"问题 → 计划 → 采证 → 分析 → 评审 → 交付"整条链路自动化、且每一步证据可追溯、失败时诚实披露而非编造的专业工作台;研究过程与成果也无法沉淀为可重开、可补证、可复用的资产。

## Solution

一个可独立运行的深度研究工作台:浏览器界面 + 本地服务,单用户、独立启动、不依赖 JuanerAI。用户创建研究项目(品牌研究或行业研究),确认研究计划后,通用研究核心以多智能体协作方式自动完成采证阅读、证据分析、报告草稿、评审修复与发布;所有关键结论绑定原文快照级证据,发布前过质量门禁(引用可验证、口径一致、反例已查、冲突已披露);资料不足或预算到顶时产出"有限交付"报告,披露限制而不编造。项目、证据、报告版本与审计记录全部本地持久化,可重开、补证、重新评审、导出(Markdown / HTML / 结构化成果包)。

## User Stories

1. 作为一名研究用户,我想创建研究项目并选择品牌研究或行业研究模块,以便研究从明确的任务框架开始。
2. 作为一名研究用户,我想在创建任务时填写研究目标、范围与已知资料,以便计划围绕我的真实问题制定。
3. 作为一名研究用户,我想上传本地资料(文本/PDF)作为输入,以便已有资料参与采证与分析。
4. 作为一名研究用户,我想在研究开始前查看并确认(或驳回修改)自动生成的研究计划(范围、问题树、方法),以便不在错误方向上浪费预算。
5. 作为一名研究用户,我想在运行中查看各阶段进度与当前活动,以便了解研究推进到哪里、大致还需多久。
6. 作为一名研究用户,我想随时取消正在运行的任务并保留已完成产出,以便及时止损。
7. 作为一名研究用户,我想在重新打开项目后从中断/取消处按阶段恢复运行,以便不重跑已完成的工作。
8. 作为一名研究用户,我想让系统在采证时自动搜索、抓取原文并保存快照,以便引用不因链接失效而无法复核。
9. 作为一名研究用户,我想查看每个问题的搜索命中与抓取失败记录,以便自行判断证据充分性。
10. 作为一名研究用户,我想在报告中展开任一关键结论的证据抽屉,看到来源、原文引句与抓取时间,以便秒级核查。
11. 作为一名研究用户,我想看到结论被标注为事实/推断/未验证,以便不把推断当事实使用。
12. 作为一名研究用户,我想看到数据带有口径(对象、时间、单位),冲突口径并列且来源得到解释,以便比较时不混口径。
13. 作为一名研究用户,我想让品牌研究模块产出品牌档案、竞品对比表与机会-风险-假设清单,以便交付物直接进入工作文档。
14. 作为一名研究用户,我想让行业研究模块产出市场口径表、行业结构与趋势-风险,以便交付物直接进入工作文档。
15. 作为一名研究用户,我想让报告在发布前自动通过质量检查(引用可验证、口径一致、反例已查),高风险问题修复并复核后才发布,以便交付质量有底线。
16. 作为一名研究用户,我想在资料不足或预算到顶时得到"有限交付"报告(披露限制与未解决问题),以便获得诚实的部分答案而非编造的完整答案。
17. 作为一名研究用户,我想看到本次运行的资源消耗(搜索/抓取/调用次数、成本估算)与停止原因,以便调整上限后重跑。
18. 作为一名研究用户,我想在工作台阅读报告并导出 Markdown/HTML/结构化成果包,以便分发与归档。
19. 作为一名研究用户,我想保存项目并在以后重新打开看到全部证据、报告与版本,以便研究沉淀为资产。
20. 作为一名研究用户,我想对已发布结论补充证据或资料并触发重新评审,以便结论随新证据演进。
21. 作为一名研究用户,我想对既有报告触发重新评审并得到新版本,以便修订可追溯。
22. 作为一名研究用户,我想查看版本列表与版本间差异摘要(结论/证据/限制的变化),以便引用正确版本。
23. 作为一名研究用户,我想查看审计日志(配置、证据、报告版本、关键执行事件),以便复盘与问责。
24. 作为一名研究用户,我想在本地配置模型与搜索供应商密钥且密钥不出本机,以便密钥安全可控。
25. 作为一名研究用户,我想用浏览器打开工作台、服务仅监听本机,以便单用户使用无需账号体系。
26. 作为一名研究用户,我想在不安装、不启动、不连接 JuanerAI 的情况下完成研究全流程,以便工具独立可用。
27. 作为一名研究用户,我想在报告旁看到完整证据清单(全部来源、快照、可信度标记),以便整体审视证据基础。
28. 作为一名研究用户,我想看到反例检查结果(对关键结论不利的证据)在报告中呈现,以便了解结论的另一面。
29. 作为一名研究用户,我想复用历史项目的目标与范围作为新任务模板,以便同类研究不从零开始。
30. 作为一名研究用户,我想让系统在换算/推导数值时使用受控数值计算(带单位与来源),以便计算值同样可追溯。
31. 作为一名研究用户,我想让抓取内容与上传资料被当作不可信内容(仅安全渲染为纯文本),以便恶意页面内容不能伤害我的机器。
32. 作为一名研究用户,我想在阶段失败时得到明确错误与已保留的检查点,以便失败不冒充完成、修复后可继续。
33. 作为一名研究用户,我想在计划确认与最终报告中看到哪些问题已回答/部分回答/未回答,以便了解研究边界。
34. 作为一名研究用户,我想让结构化成果包包含结论+依据+限制+版本信息,以便未来系统(如 JuanerAI)按契约消费。
35. 作为一名研究用户,我想在创建任务时看到预估成本与时长区间,以便决定是否启动研究。

## Implementation Decisions

- **形态与栈**:TypeScript 模块化单体;单个本地 Node 服务(HTTP API + 静态 SPA);浏览器工作台;一期仅本地部署(云部署延后)。不拆微服务(proposal 允许模块化单体)。
- **模块划分与依赖方向**:contracts(三契约与校验)/ adapters(工具适配)/ core(研究引擎状态机与阶段工人)/ stores(本地项目存储)/ quality(引用核查、口径检查、发布门禁)/ modules(品牌、行业配置)/ app(项目与 run 生命周期、预算、版本)/ server(HTTP API)/ ui(工作台 SPA)。依赖只允许 ui → app → core → adapters/stores/quality,contracts 被全部模块共享。
- **三契约字段级形态**(zod 校验、JSON 持久化):ResearchRequest = 模块类型、目标、范围、附件资料引用、预算上限、模块配置版本;ResearchRun = run id、阶段状态机状态、检查点引用、资源用量、状态(running/cancelled/failed/published/limited);ResearchResultBundle = 报告(MD/HTML)、主张-证据清单、限制与未解决问题、版本号、审计摘要。
- **引擎状态机**:阶段 plan → gather → analyze → draft → review → publish;回环 = 缺口补证、反例检查、受影响内容复核(review 可回退 gather/analyze/draft 并只重跑受影响分支)。每阶段输入输出持久化为检查点;取消 = 阶段边界安全中止 + 在飞调用超时回收;恢复 = 自最后完成阶段续跑。
- **证据模型**:SourceSnapshot(url、标题、抓取时间、正文快照、解析状态);Evidence(快照引用 + 原文引句 + 定位);Claim(陈述 + 类型 fact/inference/unverified + 证据引用 + 口径{对象、时间、单位});同一口径下多个不一致 Claim 记为冲突,发布必须带冲突披露节。
- **引用核查器**:纯函数,输入 = 报告引用清单 + 快照库,输出 = 每条引用的判定(URL 存活/引句命中/引句不符/快照缺失);发布门禁强制运行;判定失败的关键结论不得标为"已验证",只能降级为推断/未验证或触发补证。
- **发布门禁**:检查单 = 引用可验证率达标、口径一致、反例已查、冲突已披露、限制已披露;高风险问题(关键结论引用核查失败、口径冲突未解释)→ 回评审修复并复核后重过门禁;其余缺口 → 有限交付路径。原则:执行完成 ≠ 证据充分。
- **资源预算**:每 run 上限(搜索次数、抓取次数、模型成本估算、墙钟时间)+ 并行度上限,默认值可在 request 覆盖;到顶即停止发起新调用、进入有限交付;用量与停止原因写入 run 与报告。
- **工具适配层接口**:ModelProvider / SearchProvider / PageFetcher / DocParser / CalcExecutor。**模型接入统一走 `@earendil-works/pi-ai`**(统一多供应商 LLM API,OpenAI/Anthropic/Google 等);目标供应商(MiniMax/Kimi/GLM 的 OpenAI 兼容端点)的接通方式在 S1 spike 验证,若 pi-ai 无法覆盖则升级用户。搜索 = 可配置适配(MiniMax WebSearch 为参考实现);fetch + readability 正文抽取;PDF 文本抽取;本地白名单算术求值器(操作对象为带值+单位+来源引用的类型化量,不做任意代码执行);测试用 Mock/录制适配器。
- **Agent runtime(用户决策 2026-09-20,参考 https://github.com/earendil-works/pi)**:阶段工人的 agent loop 采用 **`@earendil-works/pi-agent-core` 进程内 SDK**(tool calling 与 state management),我方工具(搜索/抓取/解析/计算/证据登记)以 pi tools 形式接入;**明确不采用 pi-coding-agent CLI 子进程模式**。主控编排仍为我方 TypeScript 状态机(阶段转移确定化、可检查点、可预算强制),LLM 仅在 review 内建议回环、经编排器校验后才生效。pi-durable / pi-tui / chord 一期不采用:检查点、版本与审计由自有 stores 契约持有。
- **研究模块配置驱动**:ModuleConfig = 问题框架(问题树)+ 来源策略与验证规则 + 报告模板与结构化字段 + 专项质量检查;一期内置品牌配置(定位/价格/渠道/竞品 → 品牌档案/对比表/机会-风险-假设)与行业配置(边界/规模口径/产业链/竞争 → 市场口径表/行业结构/趋势-风险);新增研究类型 = 新增配置,不改核心。
- **本地项目存储**:项目目录 = 元数据 JSON + audit.jsonl(append-only)+ runs/<id>/(检查点、快照、用量)+ reports/v<n>/(MD/HTML/成果包);不引入外部数据库。
- **版本机制**:发布生成不可变 v<n>;补证/重新评审 = 新 run 引用旧版本,发布 v<n+1>;版本索引记录版本间差异摘要(结论增减、证据增减、限制变化)。
- **安全默认**:服务仅绑定 127.0.0.1;密钥存环境变量或本地 0600 权限配置文件;外发内容仅限研究问题与派生查询,附件资料仅在该 request 范围内发送给模型;抓取/附件内容在工作台仅以净化纯文本渲染(不执行来源 HTML)。
- **工作台页面**:项目列表;新建任务向导(模块、目标、范围、附件、预算);计划确认页(确认/驳回);运行进度页(阶段时间线、活动日志、取消);证据抽屉(结论 → 证据 → 快照原文);报告阅读与导出页;项目详情页(版本、审计、补证/重新评审入口、复用为模板);设置页(密钥与默认上限)。
- **权限**:一期单用户无登录,"权限"字段在契约中保留为 no-op 占位(团队协作与权限管理属三期)。

## Testing Decisions

- **好测试的标准**:只测外部行为 —— 给定 ResearchRequest 与适配器夹具,run 产出的 ResearchResultBundle 满足门禁判定与契约校验;不测提示词文本、不测阶段内部中间变量。
- **最高缝合点(seam)**:唯一入口 `runResearch(request, adapters, store)` —— 阶段逻辑、取消/恢复、预算到顶、有限交付全部经此入口以注入适配器测试;第二缝合点 = 引用核查器与口径检查器两个纯函数入口。理想缝合点数 = 2。
- **被测模块**:contracts 校验;core 状态机(取消、恢复、回环只重跑受影响分支、预算到顶);证据与主张管理(冲突登记);quality 三门禁;modules 配置(模板字段与质量检查完整性);stores(版本不可变、审计 append-only);app(项目/run 生命周期、复用模板)。
- **先例**:greenfield 无既有测试;建立 vitest + 录制式适配器夹具(replay fixtures)的集成测试惯例,夹具来自真实录制的搜索/抓取响应。
- **验收验证**:两个验收任务(品牌 B1、行业 I1,见 Further Notes)各以真实适配器端到端跑一次,对照 proposal 的 5 条成功标准逐条核;引用可验证率作为数字记录进验收记录。
- **红队 spike 前置**:第一条切片先做引用核查器 + 来源覆盖探针并跑真实数据(红队假设 1/2/4),其结果回写预算默认值与门禁阈值;若触发 kill 判据(评审后引用可验证率 < 80% 或必需来源可达率 < 60%)立即升级用户,不继续铺 UI。

## Out of Scope

- proposal 明确不包含:商圈研究、消费者研究、人文研究;与 JuanerAI 的集成与数据打通;账号体系、支付系统、多租户平台;复杂的插件市场与生态;消费者问卷投放、访谈招募等专项平台;企业内部知识库与业务系统对接。
- 本 PRD 进一步延后:云部署;团队协作与权限管理;LLM 调用中途崩溃的自动恢复(一期为阶段级恢复 + 调用幂等重试);多用户/登录。

## Further Notes

- **验收任务默认值**:B1 = 一个公开资料充足的消费电子品牌(品牌研究);I1 = 中国咖啡零售行业(行业研究)。用户可在验收前替换为其他真实任务。
- **红队承接**:`.flow/red-team.md` 的 5 条 kill 假设中,假设 1/2/4 由首条切片的 spike 检验,假设 3(需求)由用户访谈承接(流程外),假设 5(范围 vs 预算)由 ISSUES 拆解估时承接。
- **术语表**(PRD 与代码命名一致):主张 Claim、证据 Evidence、口径 calibration、快照 SourceSnapshot、有限交付 limited delivery、发布门禁 publish gate、检查点 checkpoint、成果包 ResearchResultBundle。
- 一期成功不以"报告看起来完整"为准,以"关键结论可核查 + 缺口被披露"为准。

## GRILL 自拷问决策记录(2026-09-20)

按 dev-flow GRILL 阶段自答(全部按推荐答案),只覆盖 proposal 未决点,不翻案已记录决策;升级项:无(无与 proposal 冲突、无可逆性风险决策)。

- **G1 agent runtime**:pi SDK 进程内接入(pi-ai + pi-agent-core),不用 CLI 子进程。理由:用户决策;进程内可类型安全地接线工具、控制检查点与预算。
- **G2 阶段 loop**:每阶段 = 一个 pi-agent-core session(阶段域 tools + prompt);阶段转移由编排器状态机决定,LLM 的回环建议须编排器校验。理由:确定化、可检查点、可预算强制。
- **G3 数据目录**:默认 `~/.deep-research/`,env `DEEP_RESEARCH_DATA_DIR` 可覆盖;项目 = 子目录。理由:单用户本地、不污染仓库。
- **G4 配置与密钥**:`<datadir>/config.json`(0600)+ `DEEP_RESEARCH_*` env 覆盖;密钥不进项目文件/日志/报告;审计记录配置 hash。
- **G5 UI 栈**:React + Vite SPA,本地服务 serve 构建产物;HTTP JSON API;dev 用 vite proxy。
- **G6 语言**:UI 与报告默认中文;证据引句保留来源语言。
- **G7 导出包**:zip = report.md + report.html(自包含)+ evidence/snapshots/ + manifest.json(主张-证据-限制-版本-审计摘要)。
- **G8 重试与幂等**:每外部调用至多 2 次重试、退避 1s/4s;超时 fetch 30s / search 20s / model 120s;调用键 = run+stage+seq,保证恢复时幂等。
- **G9 发布门禁高风险定义**:(a) 关键结论引用核查失败;(b) 比较数值口径冲突未解释;(c) 关键结论缺反例检查;(d) 证据覆盖率低于模块阈值且未披露限制。高风险 → 阻断发布、修复复核后重过;否则有限交付。
- **G10 交付分级阈值**:关键主张引句命中率 ≥ 80% = 正常交付;低于 = 有限交付(逐主张标注状态),run 不硬失败;S1 spike 期间若触发红队 kill 判据(可验证率 < 80% 或来源可达率 < 60%)升级用户。
- **G11 夹具**:验收 = 真实 live run;自动化测试 = 录制夹具 replay(经适配器录制)。
- **G12 配置版本**:ModuleConfig 带 schemaVersion;run 记录所用配置版本;已发布版本不被追溯修改。
