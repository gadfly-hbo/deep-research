| 页 1 标注 | 状态 | 实现 |
|---|---|---|
| 问题计划 → 采证阅读 → 证据分析 → 报告草稿 → 评审修复 → 发布成果(主线) | ✅ | `runResearch` 六阶段;计划经 UI 预览+**可编辑确认**后才执行 |
| 采证 ↔ 分析之间:**缺口补证** | ✅ | analyze 产出 gaps → 对未答问题自动 `gather(1, gapQuestions)` 补采一轮(`runResearch.ts:405-411`) |

## 6. 缺口清单(按影响排序)

| # | 缺口 | 方案出处 | 影响 | 后补建议 |
|---|---|---|---|---|
| 1 | **受控数值计算** | 工具适配层(§9.1-6) | 增长率/份额加总等算术结论依赖模型心算,存在算错风险(目前靠口径检查兜不一致,兜不住算术错误) | 加一个确定性计算工具:草稿阶段数值主张过表达式求值器复算,不一致打回 |
| 2 | **反证检查深度** | 02 口径与逻辑"反证";页 1 回环"反例检查" | 当前是"模型自报已做反例检查 + 未做则门禁披露",没有主动搜索反面证据的独立步骤;模型声称做了也难验证 | 评审阶段对 high 置信结论自动生成 1-2 条反例查询走搜索链,结果入证据池 |
| 3 | **受控并行** | 05 资源预算 | 采证串行是当前 10 分钟级耗时主因之一;属有意取舍(备链 MIMO 单次推理 69-199.5s,并行放大限流与超时风险) | 问题级并行度 2-3 + 全局信号量限流;主链健康时收益明显 |
| 4 | **外发授权(域名白名单)** | 06 数据与工具权限 | 抓取目标与模型调用端点未做显式白名单;本地单用户场景风险低 | 配置化 ALLOWED_FETCH_DOMAINS,抓取前校验 |
| 5 | **信源优先级未接线** | 模块配置 preferredDomains(类型已定义) | `src/modules/types.ts:21` 定义了 `preferredDomains` 但选源逻辑未使用它 | 搜索结果排序时对白名单域加权 |
| 6 | **对已完成 run 的"补充证据→重新评审"独立入口** | §8 成功标准 4 | 现在的补证形态=新建运行带附件,或评审回环内的自动 regather;没有"选中旧 run → 加证据 → 只重跑评审"的按钮 | resume 支持 merge 新附件并从 review 检查点续跑 |
| 7 | **受影响内容复核粒度** | 页 1 回环标注 | rephrase 修复是整稿重写,非"仅受影响段落"增量复核(重写后全量重新过门禁,正确性有保障,成本偏高) | 按段落锚定的增量重写 |

另有两条**已知的质量改进项**(不属方案缺口,是实测暴露):抽取保真度波动(预降级命中率 18%~78%,可上分段抽取)与 draft 长文 JSON 解析鲁棒性(已有裸 Markdown 兜底,可再强化)。

## 7. 方案之外的增量(创新点)

| # | 增量 | 说明 |
|---|---|---|
| 1 | **双供应商容灾做成"机器可判"而非"配置项"** | 方案模型层只写"主备链路·超时重试·降级策略";实现补齐了让主备真正生效的整套判定工程:瞬时故障识别(429/402/quota/5xx/超时/连接重置)、agent loop 吞错主动检出(runAgentLoop 把 429 藏进 stopReason=error 不抛异常)、连续 2 次瞬时失败熔断冷却 10 分钟、maxRetries:1 快速失败把重试权收归主备逻辑、300s 超时(按备链实测 199.5s 调定)、MIMO 无视 system 通道的兼容处理。全部来自真实故障复盘(I1 三连败根因) |
| 2 | **"有限交付"从原则变成机器门禁** | 方案只说"资料不足时有限交付,不编造";实现量化为:事实主张引文命中率 ≥80% 正常交付、否则降级有限交付;未命中主张逐条标 unverified **留档不删除**;限制披露置顶。I1 咖啡 78% 命中真实触发了这条路径并完整披露——这是整套系统最核心的差异化行为 |
| 3 | **录制/回放测试架构** | 方案未提测试;实现把适配器边界做成录制缝:live 跑一次即可离线回放真实供应商响应形状(调用键由 requestId 派生,跨 run 稳定),81/81 测试全绿且不含手写 mock |
| 4 | **双机数据共享 + 一键启动** | 方案定位"单用户独立运行";增量实现 macmini↔MacBook 经 git 通道共享 research-data/(启动拉取、run 结束自动推、退出回推、冲突 abort 保本机),外加零知识门槛的一键启动器 |
| 5 | **可靠性细节群** | 启动瞬间即落 running 记录(防"无痕消失")、服务启动清扫僵尸记录、阶段推进/每答一问实时落盘(进度条真实)、失败落档带错误信息不冒充完成——均超出方案 §9.2-04 字面 |
| 6 | **预算按问题均分算法** | `perQuestion = max(1, floor(room/remaining))`,防首问题独占预算(实测暴露后修复);属方案"调用上限"的精细化 |
| 7 | **快照唯一证据形态** | 原始 HTML 永不落盘永不下发,引用核查、证据抽屉、导出报告全链路对齐同一份纯文本快照——把方案 06"来源内容不可信"做成了单一事实源架构 |

## 8. 总评

- **忠实度**:方案 → 实现的映射是一一可查的:六阶段流程、三契约命名、八层架构、七项横向控制全部能在代码里指认到行。方案刻意排除的范围(商圈/消费者/人文研究、JuanerAI 集成、账号/支付/多租户)一样不少地留在了界外。
- **缺口本质**:仅存的 2 个 ❌(受控数值计算、受控并行)与 3 个 🟡(反证深度、外发授权、信源优先级)全部是**增强项**,不触碰一期成功标准;其中并行是有意取舍(备链慢模型下并行放大风险)。
- **超出部分**:实现的主增量不在功能广度,而在**可信度工程**——容灾判定、有限交付门禁、可回放测试、运行痕迹保全,这四块正是"研究结论敢不敢用"的决定因素。
